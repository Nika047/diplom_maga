# AGENTS.md

Обязательные правила для любого AI-агента (Claude Code, Codex и других) в проекте
ВКР «Разработка программы прогнозирования положения воздушного объекта при помощи
алгоритмов экстраполяции на основе нейронной сети». Читается всегда, целиком.

Суть проекта: прогноз положения малоразмерного самолётного БПЛА по отметкам РЛС.
Многомодельный фильтр IMM даёт базовую экстраполяцию, нейросеть-корректор её
поправляет. Сравниваются корректоры LSTM, GRU, Transformer и Mamba. Подробности -
в `.agent_docs/` (см. таблицу маршрутизации в конце). Загружать их все сразу нельзя.

## Git

Состояние репозитория - в `.agent_docs/PROJECT_STATE.md`.

- По умолчанию разрешены **только команды чтения**: `status`, `diff`, `log`, `show`,
  `branch --list`.
- `init`, `commit`, `push`, создание и переключение веток - только по явной
  просьбе пользователя в текущей сессии. Одобрение одного коммита не
  распространяется на следующие.
- `--force`, `reset --hard`, переписывание истории, удаление веток - только по
  явной просьбе. Принудительную перезапись удалённой ветки не предлагать.
- Незакоммиченные изменения считать пользовательскими. Пользователь правит файлы
  параллельно: перед правкой перечитывать файл и не возвращать то, что он убрал.
- В коммит добавлять файлы по именам.
- Не коммитить генерируемые каталоги и файлы больше 100 МБ: GitHub их не
  принимает.
- Сообщение коммита - на русском, в PowerShell через файл (`git commit -F`).

- **Библиотеки** добавлять только с согласия пользователя. Согласие действует в
  пределах сессии, в которой оно дано. О каждой установке сообщать в ответе: что

- **Обучение моделей** (этапы 2-5 в полном объёме) на рабочем ПК не запускать.
  Допустимы:
  - этапы 0-1;
  - `py_compile`;
  - смоук-тест forward/backward на малых тензорах;
  - обучение на крошечной подвыборке для проверки конвейера.
- Не выдавать `py_compile`, чтение кода или смоук-тест за проверку обучения. Если
  проверка не выполнялась - прямо это сказать.
- Не удалять данные и файлы вне перечня «генерируется» без явного разрешения. Не
  менять внешнее состояние (сеть, чужие машины, файлы вне workspace).

## Стиль

- Ответы, тексты, комментарии, документация - на русском.
- Только короткое тире (дефис) `-`, длинное тире не использовать нигде. Для

- **Python:**

  - в начале модуля docstring на русском: назначение и что проверяется;
  - комментарии редкие и короткие, только про неочевидный контракт или причину
    решения.
- Читаемость, DRY и разумный KISS. Массовый попутный рефакторинг соседнего кода -
  только отдельной задачей.

## Правила кода проекта

- **Параметры - в `config.py`.** Настройки, зависящие от устройства (окно, батч,
  эпохи, lr), - в начале `run_stageN.py`. Не размазывать числа по коду.
- **Воспроизводимость.**
  - Все случайные процессы - от `config.RANDOM_SEED` через `numpy.random.Generator`.
  - Не менять порядок обращений к генератору без согласования: сломается
    сравнимость этапов.
- **Прогоны** (`DIPLOM_DATA` x `DIPLOM_SYNTH`, версия 2): `base_x1`, `merged_x1`, затем
  `base_x4`, `merged_x4`. Каталоги результатов, кэша, весов, хранилища моделей и журналов
  у них раздельные (`config.py`), запуск одного не должен менять другой. Пути -
  только через `config.RESULTS_DIR`, `CACHE_DIR`, `ARTIFACTS_DIR`, `LOG_DIR`;
  наборы оценки - `config.EVAL_SETS`, не литералы. Новый эксперимент делается на
  обоих вариантах. Подробно - `.agent_docs/PLATFORM.md`, «Варианты данных».
- **Разбиение - только в модуле разбиения, реальные полёты - только целыми
  логами.**
  - `base`: тест - только реальные полёты; синтетика - только в train (плюс
    набор анализа); отложенный тип Z-84 - holdout, в обучение не попадает.
  - `merged`: сгенерированные траектории делятся на train / val / test по
    сценариям и добавляются к реальным; Z-84 - в общих данных, holdout нет.
  - Этапы читают готовое разбиение (`load_sets`), а не пересчитывают его.
- **Истина и измерения разделены.**
  - Истинная траектория: GPS из логов или синтетика без шума.
  - Шум добавляет только модель РЛС.
- **Входы моделей - только то, что есть в поле.** Фильтры и нейросети получают
  только отметки РЛС с временем и производные от них величины (оценки и
  вероятности моделей IMM, невязки).
  - Тип аппарата, режим полёта, углы ориентации, скорость и курс из телеметрии
    во входы не подаются.
  - Тип аппарата и режим используются только для разбиения (отложенный тип) и
    для разбора метрик.
  - Генератор не моделирует конкретные аппараты: общие ограничения класса
    самолётных БПЛА, калибровка по совокупной статистике логов.
- **Генератор физически согласован.**
  - Время считается по длине пути, скачков нет (шаг не больше `v_max * dt`).
  - Скорость, скорость разворота (не больше `g * tan(phi_max) / V`) и
    вертикальная скорость - в пределах `config.py`.
  - После любой правки генератора проверять эти ограничения.
- **Признаки и окна причинные.** Значение в момент `k` зависит только от отметок
  `0..k`. После правки проверять: признаки префикса совпадают с признаками полной
  трассы.
- **Единые модули.**
  - Метрики - только из модуля метрик.
  - Нарезка окон - только из модуля окон.
  - Определения не копировать в скрипты этапов.
- **Оценка (val/test) - без teacher forcing.**
- **Журналы.**
  - Каждый запуск пишет одновременно в консоль и в файл
    `log/<запуск>_<ГГГГММДД-ЧЧММСС>.log` (UTF-8) через общую настройку журнала.
  - Голый `print` в коде конвейера не использовать.
- **Визуализация.** Каждый этап сохраняет рисунки в `results/stageN/`:
  - PNG - для текста диплома;
  - HTML - для интерактивного просмотра.
- **Работа по этапам.**
  - Один этап - один скрипт `run_stageN.py`, один новый компонент. Прежние этапы
    целиком не переписываются.
  - Этап завершается автоматическими проверками со статусом PASS / FAIL в
    `results/stageN/summary.txt`.
  - К следующему этапу - только когда все проверки PASS, а рисунки просмотрены
    (раздел «Как проверять результат этапа»).
- Числа в документацию - только из сводок и журналов этапов.

Перед изменением кода:

1. Прочитать `.agent_docs/PROJECT_STATE.md`.
2. Посмотреть `git status` и относящийся к задаче diff - только чтение.
3. Прочитать нужные документы и исходники, не все подряд.
4. При конфликте документации с кодом доверять коду и исправить документацию.
5. Для длительной задачи вписать в `PROJECT_STATE.md` активного агента и цель.

После изменения кода:

1. Просмотреть diff и выполнить проверки, соразмерные риску (ниже).
2. Обновить `PROJECT_STATE.md` как снимок состояния, а не журнал.
3. Устойчивое неочевидное знание записать в тематический документ, удалив
   устаревшее и не дублируя.
4. Тонкости, решения с обоснованием и числа этапа, которые нужны для текста
   диплома, - в `.agent_docs/THESIS_NOTES.md` по главам. Это требование
   пользователя, делать после каждого этапа.
5. В ответе назвать результат, затронутые файлы и то, что **не** проверялось.
6. Если правка сделала неверным кусок `AGENTS.md` или `.agent_docs/`, исправить
   его в том же ответе.
7. `README.md` - описание проекта для читателя репозитория (открытый): задача,
   основные результаты, данные, установка, этапы, структура. Новый этап - строка в
   таблицу этапов; новые итоговые числа - в таблицу результатов (только из сводок).

## Проверка изменений

**Код:**
1. `py_compile` затронутых файлов.
2. Для моделей - смоук-тест forward/backward на малых тензорах: формы, loss,
   градиенты.
3. Для данных, фильтров и метрик - проверка на подставных данных с известным
   ответом.

**Как проверять результат этапа:**
1. `run_stageN.py` отработал без исключений. Журнал есть в `log/`, сводка - в
   `results/stageN/summary.txt`.
2. Все проверки в сводке PASS. При FAIL - разбираться, к следующему этапу не
   переходить.
3. Рисунки просмотрены. Что на них должно быть - в `.agent_docs/PLAN.md` у
   каждого этапа. Траектории без скачков, отметки РЛС вокруг истины, ошибки
   растут с горизонтом.
4. Результаты обучения (по присланной сводке):
   - `overfit_one_batch` и «модель обучилась» - обязательны;
   - обогнать IMM - научный результат, он не блокирует;
   - сравнивать на **том же** горизонте и наборе;
   - смотреть разрыв train/val и RMSE рядом с MAE.
